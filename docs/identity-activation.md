# AAA Identity & Access — activation runbook

Status: implemented source, NOT activated. No personal information may be committed to this public repository. GitHub Pages and current JSON catalog are public even if a browser hides a route. Do not claim this setup secures the existing site until authenticated hosting and private data endpoints are deployed.

## Architecture
- AAA Experience: users are pending by default. Admin grants enabled + experience, individually. Operations Center is an independent permission (including selected clients).
- AAA System: operator, researcher, admin. Catalog editing and cron management require independent permissions, plus server-side enforcement. Human accounts use verified identity; administration requires AAL2/TOTP. A separate private service identity registry is provided but machine authentication and API enforcement must be implemented before use.
- Auth identity and private profile, favorites, saved events, access requests in PostgreSQL. Row-level security allows only owner access to private preferences. Admin can list identities and manage access with MFA; no general access to favorites. Role cannot be written by user. Audit in private schema.
- Public catalog stores only public event/artist/venue information. Existing cron commits remain unchanged until migration of data and workers.
- Recommendations only from manually selected AAA artist IDs and explicit catalog links. No Spotify-derived profile, tokens or data ingestion. Spotify OAuth intentionally disabled pending platform policy approval, valid use case and quota review. No ad targeting from personal musical preferences.

## Before activation
1. Create an authorized Supabase project in an EU region, configure billing only with owner approval. Set up DPA, privacy notice (responsible entity, contacts, purposes, legal bases, retention, processors/transfers, rights, complaints), retention and account deletion process. Determine whether minors are permitted and safeguards required. Never enable account forms before this.
2. Apply migration in `supabase/migrations/20261127194500_aaa_identity.sql` to a test database; perform RLS tests with two users, anonymous requests, pending/revoked roles, admin with/without AAL2, attempt role escalation, and verify deletion/export procedures. Verify email, email rate limits, CAPTCHA and abuse protections, configure production SMTP. Restrict callback URLs to exact deployment origin/path.
3. Set Supabase Site URL to final trusted deployment origin. Configure email magic link, Google OAuth client and callback in Google Cloud and Supabase; other providers only when actually configured (Apple, Microsoft, GitHub, Discord, Facebook, LinkedIn OIDC). Store provider client secrets in Supabase, never GitHub or JS. For Google use the callback supplied by the Supabase dashboard. Confirm OAuth consent screen.
4. Bootstrap first administrator through trusted SQL console AFTER that person registers/verifies email. Use their verified UUID, never an email guessed from public data. Example: `update public.aaa_access set role='admin',enabled=true,experience=true,operations=true,catalog_edit=true,cron_manage=true where user_id='<VERIFIED-UUID>'::uuid;` Enroll TOTP and verify AAL2. Do not commit UUID/email or production configuration secrets.
5. For public preactivation page `identity-config.js` may hold only Supabase project URL and sb_publishable key, allowed provider names, approved privacy notice URL/version. Enable only after steps above. No service_role or OAuth secret in client code. Bundle pinned dependency locally and set CSP in production; current module loads pinned Supabase JS from CDN only after activation.
6. **Mandatory for access protection**: migrate AAA Experience and Operations Center to a server/edge host with verified sessions and server authorization on each page and data/API request. Move any restricted catalog/operations data to a private store and remove public serving from GitHub Pages/repo (existing public copies cannot be made confidential retroactively). Use HTTP-only secure session cookies, appropriate CSRF controls, TLS, MFA for privileged actions and separate narrowly scoped machine credentials. Deny by default when permission lookup fails; recheck enabled + experience or operations on each request. Ensure anonymous users cannot read restricted data or HTML directly. No JS-only gating. Migrate the portal without breaking data ingest. Existing public app remains available until authorized cutover; never publish private data there.
7. Implement secured catalog write endpoints, worker tokens / secret rotation, least-privilege permissions, audit events, monitoring and retention. Implement privacy-request processing (export, deletion), including revocation and retention rules. Then validate sign-in, logout, session expiry, user isolation, access revocation, OAuth callback, MFA and full production route security.
